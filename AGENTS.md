# Prototype Instructions

Reports run on the owner's command only. Follow `REPORTING_PROTOCOL.md`. The separately authorized recurring task captures data privately. A missing or unverified framework metric blocks report preparation, dashboard updates and email. Recheck the native source and device sync, then ask for the exact access or export needed if the metric remains unavailable. Save partial observations as private diagnostics. Send email only when requested. Read the recipient and credentials from private configuration. Never publish the owner's health data, source captures, encrypted payloads, private report URLs or credentials to this public repository.

Use professional cycling-coaching analysis with explicit evidence, uncertainty and adjustment rules, without claiming a UCI credential. Verify source access and capture times for each run. Separate today's partial observations, completed-day comparisons, provider-specific load models and unverified estimates. Never present a browser or extraction service as authenticated unless its own observed result proves it.

The next-day workout simulator uses an explicitly labelled Intervals-style fitness/fatigue model. Never present its ATL/CTL ratio as a Garmin forecast or apply Garmin ratio bands to it. A separate "Tomorrow if I rest" card estimates Garmin load changes from captured consecutive-day acute/chronic transitions with no recorded activity, including both components changing. It requires dated history and complete activity coverage, excludes the current partial date and all recorded activity dates, keeps numerator/denominator changes paired, and labels the result low confidence with an empirical scenario spread and extrapolation warning. Missing history stays unavailable. Never substitute fixed 7/28 exponential assumptions for Garmin's undisclosed model, guarantee a falling ratio, or publish the private calibration data. Preserve remaining-today chronology, captured activity-type weights, editable assumed time constants, load uncertainty, historical-snapshot dates and recovery checks. The owner chooses activity, duration and effort; expected load and ranges are calculated outputs, with no manual point entry. Effort must update the load estimate using explicitly disclosed same-sport historical rate bands, not only change a warning. These relative effort proxies are not measured RPE, validated zones or an invented RPE-to-HRSS conversion. Missing or unvarying history must stay explicit rather than fabricating effort separation. The planner must not recommend intensity merely to fill a load score or ratio.

The selected visual target is Performance Desk with near-black surfaces, rounded instrument panels, crisp numeric readouts and bright cyan, lime, pink, violet and amber metric signals. Use restrained glow only for actual data marks. Keep chart signals distinct and numeric contrast strong. Begin with body condition and the coaching decision, then show the next-session plan and pacing. The owner prefers a fast scan of all important metrics actually recorded in the selected report, without a seven-day activity restriction. Show recovery, sleep/vitals, Garmin load, separate Intervals model values and fitness/adaptation context. Keep per-reading source dates/capture times, unavailable fields and recorded recovery-time snapshots explicit; compilation or a load-history supplement must not silently refresh wellness. GitHub hosts the public source and viewer. Personal report data stays in local private files and emailed URL fragments; never publish personal ciphertext or keys to GitHub. The archive is local to the browser that opened each report. Buildkite is excluded from the workflow.

Open the Performance Desk shell directly. When no report is open, show a compact empty state with a link to ChatGPT Library. Keep Request report available at the top and show report loading or link errors within the shell.

Keep Request report near the report date when a report is open. It prepares the owner's on-demand prompt in ChatGPT for review and submission in Work. The public site carries no account-specific report links, keys or email addresses and does not submit or generate a report itself.

Open private links automatically and resume reports in the same unlocked browser session. Preserve the exact report selected by an incoming email, even when newer reports are cached. Place the session plan before charts. Keep historical capture dates clear, Lock available while unlocked, full activity-history filters, and completed-calendar-day comparisons with explicit source coverage. Chart code is loaded separately from the initial dashboard bundle.

Use a compact, experienced-athlete interface across every page. All interface copy is English with standard training terms (RHR, HRV, CTL, ATL, TSB, RPE, TL). Prefer numeric readouts, source-status colors, real recorded-history plots, sleep-stage composition, baseline bands and session timelines over prose. Garmin-inspired blue, green, orange, red and purple identify metrics/status; readiness colors follow Garmin's published categories, while other provider models keep their own semantics. Do not invent histories, targets, ratio zones or measurement dates. Keep inline text to essential labels, units, dates, missing/estimate states and actionable session targets. Consolidate technical definitions, calculations, source provenance and field verification in the Reference page. No repeated disclaimer paragraphs. Preserve calculation engines and automatic load estimation.

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

Use one Performance Desk heading and one report timestamp. Keep Daily, Trends and Archive focused on numeric readouts and graphics. Weekly totals and session adjustment rules may expand inline; explanatory coaching analysis belongs in Reference. Forecasts use compact Est. markers, with confidence and calibration in Reference. Unknown source statuses use neutral gray.

Daily focuses on recovery, actionable coach suggestions, and check-in. The coach may combine training, food, recovery or rest, with a practical alternative and reassessment trigger. Link the dated data signals to peer-reviewed evidence in Reference. Trends groups HR time in zone by sport, Garmin Load Focus points and targets, recovery history, and cycling load. Show points below, within or above each verified target band, with chart-derived bounds identified. Keep volume and activity history collapsed. Show HR zone capture coverage, preserve dated provider windows, and compare weekly cycling volume over six completed seven-day blocks. RHR Δ uses the preceding 28-day median with at least seven prior readings. Sleep gap uses the need for the completed night.

Benchmarks groups verified segment efforts, recorded lap or interval details, provider PRs, VO₂ max, and speed or pace. Match segment efforts by provider and segment ID, and speed or pace by sport, activity scope and timing basis. Preserve measurement date precision, including monthly buckets. Recheck blank readings at their source, attach available values with provenance, and show remaining gaps in Reference. Keep details expandable and provider estimates separate from measurements. Use a subdued slate gradient with deeper Garmin-inspired semantic colors.

Plan contains the seven-day Intervals scenario and the expandable next-day load simulator. Preserve the dated baseline, contribution weights, remaining-today chronology, automatic sport-duration-effort TL, exact per-session CTL/ATL covariance in TSB ranges, and separate rest reference. Do not predict future wellness or present scenarios as prescriptions. Session check-ins record RPE, leg soreness and fatigue without default zero; sRPE load is actual timer minutes × RPE in AU, separate from provider loads. Encrypt check-ins before browser persistence; demo entries stay in memory. No report generation, schedule or email is triggered by these controls.

Numeric readability takes priority over squeezing cards into one row. Use large primary values, consistent padding and clear baseline alignment. Keep every sign, percentage, unit and denominator visually attached to its number in a nonwrapping numeric group; metadata may wrap separately. Use compact h/m duration readouts with smaller inline units. Adjust responsive columns when values need room. The shared readability.css layer owns these refinements, including lazy feature pages.

The owner may choose an access code for report links. Use a code prompt without account sign-in, keep the code and report material private, and carry only encrypted report data and a wrapped archive key in the link fragment.

Attach optional threshold review, pacing evidence and progression to newly verified reports. Each pacing target needs its own source, evidence date and confidence. Distinguish a capture date, a measurement date and a configured setting. Keep power processing and device-specific running estimates identified. Match planned versus actual by provider activity ID, sport, activity date and steady work-block scope. Missing work-block evidence stays unavailable. Change provider thresholds or zones only when independently supported by sport-specific evidence.

Match Trends to Daily through shared panel and metric-card styling. Give data cards a keyboard-accessible detail dialog with available readings, capture context and source. Keep in-card filters, links and other controls independent. Draw Body Battery daily low–high ranges as cyan stems with endpoints and keep unrecorded days blank. Smooth continuous lines with monotone curves through their recorded points, including Garmin Training Load. Retain gaps, actual extrema, and discrete bar or point encodings. Use the access-code-only screen and keep private report links and data outside the public build.

Card dialogs offer dated history in seven-day, four-week, three-month and all-history ranges. Keep recorded values on their measurement dates and show coverage gaps. Body Battery daily lows and highs come from Garmin Connect. Keep full provider exports private and retain each provider's coverage and collection status. Estimate steady-effort heart rate from paired cycling power, running pace or watch power recorded in comparable blocks. Show source, dates, evidence count and confidence for each estimate. Test on later days and mark estimates unavailable when support is insufficient.

Open card dialogs with the recorded chart above its historical table. Keep device and methodology details available below the table. Leave missing days blank, distinguish sessions or occasional records from daily series, and use numeric values on their original scales.

Use narrow segmented bars for bounded readiness scores, a compact ring for sleep score, and a segmented half-circle for heat acclimation when recorded. Give measured trend charts quiet dashed guides and clear date/value labels. Keep the existing metric colors and use fill only under continuous recorded runs.

Use equal left and right gutters for the header and report, and reduce spacing between related cards without shrinking numeric readouts. Use consistent cyan for cycling power, lime for running pace and pink for heart rate in Predictions. Show paired observations as points. Keep both pacing prediction directions visible, each with its own confidence and chart-first evidence history. Check recovery against the dated capture before suggesting a workout.

Use 12 columns on desktop with 80–120 px gutters or a centered maximum-width container, 8 on tablet with 40–80 px gutters, and 4 on mobile with 16–32 px gutters. Align header and content to the same edges and keep the Garmin load chart beside the recovery suggestion on desktop. Apply the established slate, rounded-panel visual system and semantic metric colors to this structure.

Show Helicopter Lift on Daily when Garmin strength sessions are available. Open the session-volume chart first, then the session table, the heaviest logged set per exercise, and equipment illustrations. Keep unnamed sets in the volume and show their heaviest load separately.
