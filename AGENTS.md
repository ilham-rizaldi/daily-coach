# Prototype Instructions

Reports run on the owner's command only. Follow `REPORTING_PROTOCOL.md`. Do not enable schedules, background refreshes, automatic email, or report-generation hooks on GitHub pushes. The current command may invoke the owner's already authorized full report-and-email protocol; do not ask for the same authorization again. Otherwise prepare and show the report, and send email only when requested. Read the recipient and all credentials from private configuration. Never publish the owner's health data, source captures, encrypted payloads, private report URLs or credentials to this public repository.

Use professional cycling-coaching analysis with explicit evidence, uncertainty and adjustment rules, without claiming a UCI credential. Verify source access and capture times for each run. Separate today's partial observations, completed-day comparisons, provider-specific load models and unverified estimates. Never present a browser or extraction service as authenticated unless its own observed result proves it.

The next-day workout simulator uses an explicitly labelled Intervals-style fitness/fatigue model. Never present its ATL/CTL ratio as a Garmin forecast or apply Garmin ratio bands to it. A separate "Tomorrow if I rest" card estimates Garmin load changes from captured consecutive-day acute/chronic transitions with no recorded activity, including both components changing. It requires dated history and complete activity coverage, excludes the current partial date and all recorded activity dates, keeps numerator/denominator changes paired, and labels the result low confidence with an empirical scenario spread and extrapolation warning. Missing history stays unavailable. Never substitute fixed 7/28 exponential assumptions for Garmin's undisclosed model, guarantee a falling ratio, or publish the private calibration data. Preserve remaining-today chronology, captured activity-type weights, editable assumed time constants, load uncertainty, historical-snapshot dates and recovery checks. The owner chooses activity, duration and effort; expected load and ranges are calculated outputs, with no manual point entry. Effort must update the load estimate using explicitly disclosed same-sport historical rate bands, not only change a warning. These relative effort proxies are not measured RPE, validated zones or an invented RPE-to-HRSS conversion. Missing or unvarying history must stay explicit rather than fabricating effort separation. The planner must not recommend intensity merely to fill a load score or ratio.

The selected visual target is Performance Desk: charcoal background, lime accents, a body-condition overview at the top, a coaching decision, readable charts and a next-session plan. The owner prefers a fast scan of all important metrics actually recorded in the selected report, without a seven-day activity restriction. Show recovery, sleep/vitals, Garmin load, separate Intervals model values and fitness/adaptation context. Keep per-reading source dates/capture times, unavailable fields and recorded recovery-time snapshots explicit; compilation or a load-history supplement must not silently refresh wellness. GitHub hosts the public source and viewer. Personal report data stays in local private files and emailed URL fragments; never publish personal ciphertext or keys to GitHub. The archive is local to the browser that opened each report. Buildkite is excluded from the workflow.

The locked login page shows only the Performance Desk eyebrow, the two-line "Your training. Your private report." heading, the private-link instruction, the access-key input and the Open my report button. Do not show the global header, extra privacy paragraph or design-preview link on this screen. Show errors and loading state only when needed.

The same minimal form accepts a complete private email link or a key for reports already saved on the device. Preserve the exact report selected by an incoming email, even when newer reports are cached. Place the session plan before charts. Keep historical capture dates clear, Lock available while unlocked, full activity-history filters, and completed-calendar-day comparisons with explicit source coverage. Chart code is loaded separately from the initial login bundle.

Use a compact, experienced-athlete interface across every page. All interface copy is English with standard training terms (RHR, HRV, CTL, ATL, TSB, RPE, TL). Prefer numeric readouts, source-status colors, real recorded-history plots, sleep-stage composition, baseline bands and session timelines over prose. Garmin-inspired blue, green, orange, red and purple identify metrics/status; readiness colors follow Garmin's published categories, while other provider models keep their own semantics. Do not invent histories, targets, ratio zones or measurement dates. Keep inline text to essential labels, units, dates, missing/estimate states and actionable session targets. Consolidate technical definitions, calculations, source provenance and field verification in the Reference page. No repeated disclaimer paragraphs. Preserve calculation engines and automatic load estimation.

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

Use one Performance Desk heading and one report timestamp. Keep Daily, Trends and Archive focused on numeric readouts and graphics. Weekly totals and session adjustment rules may expand inline; explanatory coaching analysis belongs in Reference. Forecasts use compact Est. markers, with confidence and calibration in Reference. Unknown source statuses use neutral gray.

Trends includes dated recovery history, provider-confirmed PRs, source- and sport-specific VO₂ max, and average speed or pace by activity scope and timing basis. Preserve the source and precision of dates, including monthly export buckets. Recovery history comes from validated source data. RHR Δ uses the preceding 28-day median with at least seven prior readings. Sleep gap uses the need for the completed night. Cycling progression uses six completed seven-day blocks, canonical timers and Intervals-only activity load. The capture date is excluded from cycling weekly comparisons. Recheck blank readings at their source, attach available values with provenance, and show remaining gaps in Reference metric coverage. Keep activity detail expandable and provider estimates separate from measurements.

Plan contains the seven-day Intervals scenario and the expandable next-day load simulator. Preserve the dated baseline, contribution weights, remaining-today chronology, automatic sport-duration-effort TL, exact per-session CTL/ATL covariance in TSB ranges, and separate rest reference. Do not predict future wellness or present scenarios as prescriptions. Session check-ins record RPE, leg soreness and fatigue without default zero; sRPE load is actual timer minutes × RPE in AU, separate from provider loads. Encrypt check-ins before browser persistence; demo entries stay in memory. No report generation, schedule or email is triggered by these controls.

Numeric readability takes priority over squeezing cards into one row. Use large primary values, consistent padding and clear baseline alignment. Keep every sign, percentage, unit and denominator visually attached to its number in a nonwrapping numeric group; metadata may wrap separately. Use compact h/m duration readouts with smaller inline units. Adjust responsive columns when values need room. The shared readability.css layer owns these refinements, including lazy feature pages.
